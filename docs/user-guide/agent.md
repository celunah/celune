# Agent mode

Agent mode is a bounded local task runner built on Persona. It is not an
arbitrary shell or computer-control agent. The runtime exposes typed,
allowlisted operations, validates every call against its schema, and routes
mutating work through approval policy.

Agent mode requires at least the `high` VRAM preset with a standard Persona
model. Registered smart 8B-tier Persona models require `xhigh`. At `high`, the
agent context is capped at 8,192 tokens. If a lower preset is selected, agent
routing is disabled rather than raising the configured preset automatically.

## Task lifecycle

An agent request can move through `queued`, `idle`, `classifying`, `working`,
`planning`, `executing_tool`, `responding`, `awaiting_approval`,
`awaiting_choice`, `paused`, `interrupted`, `cancelling`, `cancelled`,
`completed`, or `failed`. Approval and choice pauses preserve the task and do
not consume an iteration. Cancellation clears pending approval/choice state.

The production limits are:

- 20 tool/planning iterations per task.
- Up to 8,192 tokens of agent context space.
- Up to 256 output tokens for input classification, with one repair attempt for
  rejected output.
- Compaction pressure around 6,144 tokens by default, controlled by the shared
  `persona.compact_at` setting.
- A stuck-task threshold of three repeated non-progress outcomes.

The agent can speak its final result through the standard `say()` path. The
`speak` tool waits for playback to finish before returning, so later agent
utterances and terminal failure replies do not overlap it. Tasks can also be
paused, resumed, cancelled, or queried by the runtime and extension events.

A new task begins with a short acknowledgment generated by Persona in the
active character's voice. Its prompt requires an acknowledgment only, without
claims that work has started or results are known. If generation fails, the
runtime uses a randomly selected localized fallback. The first planning message
is not spoken before tool selection. The task enters its classification state
before the opener is spoken, keeping the agent status active during speech.
If Persona is still initializing, a new task stays idle until Persona finishes
loading and releases its VLM lock. Planning starts afterward.
Tool results and the final response continue through the normal speech path.
Speech delivered as part of an ongoing agent action preserves the active status
when playback completes, so an intermediate response does not make the agent
appear idle before its task ends.
When a task ends after its final playback, the engine returns the status to
Idle.

Agent prompts do not include Persona's automatically retrieved long-term
memories, conversation summary, or ordinary chat history. Memory tools remain
available when a task explicitly needs a memory operation.

## Built-in engine tools

The normal production catalog is always local and explicitly registered:

| Tool family | Calls |
| --- | --- |
| Status | `read_agent_status`, `query_status`, `query_capabilities`, `query_models`, `query_locks`, `query_audio_state`, `query_agent_task`, `run_health_check` |
| Speech | `speak`, `clear_speech_queue` |
| Voice and character | `set_voice`, `set_voice_prompt`, `set_playback_speed`, `set_reverb`, `set_character`, `query_character` |
| Routing and lifecycle | `set_conversation_mode`, `set_agent_mode`, `sleep`, `wake` |
| Persona memory | `remember`, `recall`, `forget`, `clear_recent_context`, `summarize_context` |
| Task status | `query_task`, `query_task_history` |

The agent cannot interrupt active speech or pause, resume, or cancel its task.
Runtime and extension controls own those lifecycle transitions so a tool call
cannot interrupt its task's control flow.

Important argument constraints include:

- `speak.text` is required and successful speech ends the task.
- `set_playback_speed.speed` is 0.25 through 4.0.
- `set_reverb.strength` is 0 through 1.
- `remember.importance` is 1 through 3.
- `recall.limit` is 1 through 20.
- `set_conversation_mode.mode` must be `converse`; `set_agent_mode.mode` must
  be `agent`.

Every mutating tool has `approval_required: true` in its typed schema. The
read-only tools return JSON-compatible diagnostics and do not access arbitrary
files.

## Optional local-management tools

The local filesystem and process catalog is controlled by
`agent.fs_tools: true`. It creates an unsandboxed capability boundary, so the
runtime emits a warning when it is enabled.

| Tool family | Calls | Policy |
| --- | --- | --- |
| Filesystem read | `local_current_working_directory`, `local_list_directory`, `local_file_metadata`, `local_read_text` | Absolute or working-directory-relative paths; non-recursive listing; text bounded to 1 MiB. |
| Filesystem mutation | `local_write_text`, `local_make_directory`, `local_copy` | Medium danger and approval required. |
| Filesystem destructive | `local_move`, `local_delete` | High danger; exact absolute target; recursive delete must be explicitly enabled. |
| Process diagnostics | `local_list_processes`, `local_inspect_process`, `local_system_info` | Read-only, bounded diagnostics; system information includes detected CUDA device names, capability, and memory. |
| Process control | `local_launch_process`, `local_terminate_process` | High danger; structured arguments, no shell, and identity checks. |
| Application discovery/control | `local_discover_application`, `local_running_applications`, `local_launch_application` | High-danger launch operations; close a verified application with `local_terminate_process`. No GUI automation. |

Read-only filesystem paths may be absolute or relative to Celune's process
working directory; Celune resolves them before access. Filesystem mutation
paths must remain absolute so approval identifies the exact target. Process
and application termination requires an expected name so a stale PID cannot
be used blindly. The agent never turns a free-form prompt into a shell command.
Process launch resolves executable names through `PATH` and, on Windows, also
checks the Windows system directories. Arguments are passed as a structured
list, and shell execution remains disabled.
Routing and tool-selection prompts instruct Persona and Needle to preserve
explicit paths from the task request. Celune also retains the original user
request when Persona produces a shorter task summary, so the selector and local
filesystem tools can still use the exact requested operation and path. When a
request clearly names an operation, Needle gives tool-name matches more weight
than generic description or argument matches, reducing confusion between
similar tools such as directory listing and creation. When a
request contains the number of unambiguous absolute paths expected by a
filesystem tool, Celune uses those exact paths even if Needle supplies
corrupted or different paths. Copy and move use exactly two requested paths in
source-then-destination order. Recovered paths are applied before approval so
the prompt identifies the requested target. Sentence punctuation after an
unquoted path is ignored; quote paths when punctuation is part of the target
name. Requests with an ambiguous number of paths are not rewritten.
For a successful directory listing, Persona is instructed to include the
resolved path and returned entries in its final answer. It is also instructed
to identify empty and truncated listings and preserve entry names exactly.

## Needle tool selection

Production agent mode uses the Needle selector when its verified checkpoint is
available. The checkpoint is validated and prepared in an isolated cache; a
legacy JAX/Flax `needle.pkl` is not accepted as a normal production artifact.
An input beginning with `Use`, `Call`, `Run`, or `Invoke` followed by a
registered tool ID routes directly to that exact tool request.
Needle may select only registered schemas, and the runtime validates names,
argument types, approval state, and availability before execution.
An explicit `Use <registered_tool_id> ...` request restricts selection to that
registered tool. Otherwise, request-to-tool relevance narrows the catalog before
selection. Identical returned calls collapse to one call. Celune asks the user
only when Needle returns multiple distinct calls that remain ambiguous.
The numbered options show each tool and its arguments in speakable form: empty
objects are described as having no arguments, and populated JSON is rendered
as named values instead of reading braces and quotes aloud. The user can
identify an option in their response. Celune executes only the selected call,
then applies the normal availability and approval checks. The choice pause does
not consume an iteration or trigger another planning step.
Needle integer arguments normalize exact whole-number values and numeric strings
to integers; `null` optional arguments and optional values with the wrong type
are omitted so the registered default applies. Invalid required values remain
errors. Before selection, the selector uses request-to-tool keyword overlap to
form a candidate set. A clear match leaves Needle one tool choice; otherwise it
includes up to eight ranked tools. If the request and action intent have no
lexical overlap with the catalog, all available tools remain candidates. If the
selector receives no call, it retries with a compact instruction and the same
candidate schema; when the set was narrowed, it then retries once with the full
catalog.
Oversized catalogs have their lower-ranked argument and tool descriptions
removed first; lower-ranked definitions are omitted only if the remaining typed
schemas still do not fit. Needle receives the original user request with
Persona's action intent, even when task classification produced a shorter
summary. It retries with the original request alone if needed. The selector
allows up to 256 generated tokens. If no available
tool exists or even one minimized definition cannot fit, selection fails before
asking Needle to choose from an empty catalog.
If a selected call omits required arguments, the selector reconsiders the choice
against the candidate set, then the full catalog if that returns no call. It
passes the original request, Persona's action intent, and up to 1,024 characters
of the previous tool output, and tells Needle not to invent missing values.
Missing-argument errors identify the selected tool by name.
The loader instantiates the model in the dtype declared by its validated
checkpoint before placing it on the selected device, avoiding an intermediate
FP32 copy for BF16 checkpoints.
Needle's KV cache grows with generated tokens and lasts only for that selection
request. Rotary values are computed for the prompt or decode step in use;
`max_seq_len` is a hard limit and does not reserve a full positional table.

## User steering and approvals

The UI displays approval and choice requests as task states. Persona speaks a
character-voiced explanation of the exact pending action before asking for
approval. Short answers such as `yes`, `approve`, `go ahead`, `no`, and `deny`
are handled directly; unclear answers leave the request pending and ask again.
Iteration and task status refresh as the runtime advances, including while
agent speech is playing and after the task returns to idle. Persona generates
opening acknowledgments using the active character's guidance. If an opening
claims status, progress, or unsupported facts, Persona is asked to regenerate it
once; a second invalid opening is not spoken. Punctuation-only responses are
retried once and never sent to speech. Tool-result replies are prompted to
report only facts present in the structured result. Approval pauses do not
increment the iteration;
the counter advances when the approved tool begins execution.
The user can also provide a clarification, pause, resume, or cancel the task.
Extensions can subscribe to `agent_approval_requested`,
`agent_choice_requested`, `agent_task_state_changed`, and
`agent_task_finished`. See [Extensions](../interfaces/extensions.md) for the
event payloads.

## Verify agent availability

Run `celune test agent` to check the configured live agent path, every active
tool handler, schema validation, permissions and approvals, task lifecycle,
choices, context limits, and terminal outcomes. Its report records each check
as passed, failed, or skipped. Optional local-management checks run only when
`agent.fs_tools` is enabled. The [CLI guide](../interfaces/cli.md#commands)
describes the report and exit status.

After the live task, the test invokes every active tool with isolated test
adapters and speaks a short status for each tool; the detailed result is
recorded in the test log. Celune then speaks a multiple-choice request and an
approval request before displaying each request and accepting a typed answer.
The answer is applied directly to the paused diagnostic runtime, so the check
verifies that the response was received and processed without requiring another
Persona response. Either listed choice is accepted, and approving or declining
the simulated mutation passes when processed. The answer field says “Enter your
answer here,” with “Waiting for answer” and “Processing answer” status messages.
These spoken tool results and interactive prompts apply only to
`celune test agent`. Each typed response has a two-minute timeout; no response
fails that check.
